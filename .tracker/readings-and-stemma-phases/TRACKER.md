# Tracker for readings-and-stemma-phases

## Purpose

This document tracks the status of all tickets in the epic. Goal: make the CBGM data entry phases — Readings and local stemmata — completable, trustworthy, and worth completing. Today editorial decisions are recomputed from normalized-text equality on every write so they do not persist; the subreading attachment control silently no-ops for every case a scholar would reach for; the local stemma diagram overlays citation structure with genealogy in a fixed two-row layout and cannot be operated without a mouse; a lacuna is treated as a reading; nothing in either phase is undoable; and nothing anywhere consumes the result. Spec: `SPEC.md` in this directory.

The shape of the fix: separate the reading proposal from editorial decisions, reframe Readings around bulk witness selection, present the local stemma as an auto-laid-out single-source tree over arc-based storage, and end the flow in a Review phase with a reconstructive TEI apparatus validated against TEI P5. Geometry, the decision overlay, and apparatus rendering move into pure modules tested in the node project; the components become thin.

## Ledger

Ticket 01 is a pure prefactor with no behaviour change — it makes everything after it a small change. Ticket 02 is the tracer bullet: it carries one decision kind end to end, proves the proposal/decision architecture, and fixes the headline bug on its own. Tickets 03, 04, and 05 then add decision kinds along the path 02 establishes and are **independent of each other** — they can run in parallel. Ticket 06 needs the completed reading model to render, and 07 consumes it. Ticket 08 deliberately delivers the accessible source-decision route before 09 adds pointer and keyboard graph gestures, so the stemma phase is fully operable even if 09 slips. Ticket 11 is the payoff and needs both the renderer and finished stemmata. Ticket 12 is research, gates nothing, and can run at any point.

The critical path is 01 → 02 → 05 → 08 → 10 → 11.

| 2026-08-14 | Ticket `04` completed. A reading now carries an evidential **reading type** from an open, project-extensible vocabulary (`reading-types.ts`: omission, deficient, apparent, nonsense, orthographic, plus whatever a project adds through `ProjectCollationSettings.readingTypes`) and an orthogonal `certainty`. Both are proposed then decided: `proposeReadingType` derives a type from evidence the pipeline already carries — omission from the aligner, `deficient` from segments the transcriber marked unclear or supplied, `nonsense` from a `ns`-typed regularization rule having fired — and `UnitDecisions.readingType` / `.certainty` ride the ticket-02 overlay, so a recorded value outranks the proposal, a recorded `null` means "no type" rather than undecided, each write is one undoable command, and a decision naming a vanished reading orphans instead of disappearing. The incoherent control is gone: the readings-phase Type select now reports exactly what it writes, offers only genuine editorial judgements (omission is shown when the aligner determined it but cannot be picked, and `lac` — ticket 03's leftover hand-created lacuna — is retired, so nothing in the app sets `isLacuna` on a reading any more), and **no type change touches `text` or `normalizedText`**, which removes the silent text destruction rather than gating it behind a confirmation. `ReadingClassification`, `classifyReading`, and the stemma node tinting derived from it are deleted; nodes take one neutral colour until ticket 08 gives colour a meaning. Subreadings carrying no type are recorded through `getSubreadingsMissingReadingType()` for ticket 11 to surface. Reading types no longer follow family position: promoting a family member keeps each reading's own type, which corrected three specs that had asserted the old blanket `ns`. New signals (`hasUnclear`, `hasSupplied`) are computed on the reading buckets from `originalSegments`, and the proposal specs are driven through the real adapter — both were confirmed red against a mutated proposer before being relied on. Adversarial review then caught four defects, each fixed behind a spec confirmed red against the pre-fix code and driven through the real collation adapter rather than hand-built cells. **(1)** Every mutator hands the decision-applied view back to `setReadingsForUnit`, which stores it as the proposal, so a recorded type or certainty was welded into `classifiedReadings` — it survived its own undo, stopped re-deriving when its evidence changed, and was what `buildApparatus` persisted. `setReadingsForUnit` already restored `parentReadingId`/`isSubreading`/`autoGenerated` for the same reason in ticket 02; it now restores every field a decision can overlay, and the round-trip spec runs through the undo rather than stopping at the edit. **(2)** The reading bucket key folded segment text and `hasUnclear` but not `isSupplied`, so under the default `suppliedTextMode: 'clear'` a witness reading `λ[ογος]` bucketed with witnesses reading `λογος` intact, `hasSupplied` was OR-ed across the bucket, and `proposeReadingType` returned `deficient` for all of them — asserting of an undamaged base text that its reading is only partly identifiable. `isSupplied` is now part of the key, as `hasUnclear` always was. **(3)** `coerceReadingTypeDefinitions` let a project blob `{ id: 'omission' }` default `selectable` to true and so put omission back in the menu; the parser now takes a bundled type's selectability as authoritative and lets a project override only its label and description. **(4)** `reset()` did not clear `projectReadingTypes`, so `createProject` copied one project's vocabulary into the next one created. The stemma phase's stale "Reading Classification" heading and comments are gone. A note went to ticket 11 recording that the legacy TEI exporter emits `readingType` as `@type` without distinguishing a proposal from a decision, which ticket 11 must rule on when it replaces that exporter. Left alone as out of scope: the `persistRulesToProject` race and the identical pre-existing sloppiness for witness treatments. Server suite (629 tests), client browser project (249 tests), and `pnpm check` pass; `pnpm lint` is unchanged from baseline (the `no-useless-assignment` error in `reference-editions/insertion.ts` and 21 unused-var warnings). | 2026-08-11 | Ticket `02` rewritten after an architecture review, and `SPEC.md` corrected. Two findings. First, an **editorial decision** had no durable address as well as no durable identity: decisions and stemma edges are keyed by `getReadingUnitKey`, which returns a position in `alignmentColumns`, while `mergeColumns`, `splitColumn`, and `shiftToken` all reindex that array and touch neither map. Second, `SPEC.md` claimed re-running an alignment stops destroying editorial work. It cannot: `collation-adapter.ts` assigns every column a fresh `crypto.randomUUID()` per run, so nothing column-derived survives a re-collation and reattaching needs a content-derived anchor nobody has designed. The SPEC now scopes the claim to hand edits and states the re-collation gap explicitly, and ticket 02 forbids inventing an anchor. `CONTEXT.md` gained a **Variation unit** entry. |
