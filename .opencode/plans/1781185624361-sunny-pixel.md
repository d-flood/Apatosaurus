# Project-Centered Storage, Versioning, and Sync Architecture Plan

Superseded operational entry point: `plans/00-project-centered-sync-overview.md`.

Read the overview first when continuing implementation. This file is retained as the original umbrella planning note; the overview in `plans/` contains current handoff instructions and progress tracking.

## Purpose

Break the cloud-storage/transcription/collation concerns into separable subplans. This is intentionally not one implementation pass. Each subplan defines a stable boundary that can be expanded into a detailed coding plan later.

## Current Grounding

- Local persistence is SQLite in OPFS through `app/src/lib/client/db/*`.
- The product model should treat `Project` as the top-level aggregate. Project work is restored, backed up, removed, forked, and browsed as whole projects, not as independent transcription or collation files.
- Both transcriptions and collations are project-associated data. A project backup must contain the full transcription data and full collation data required to restore the project without dangling references to a separate transcription library.
- The current schema still uses `transcriptions.scope_type = 'project_snapshot'` and `project_transcriptions` for project-owned transcription rows. Treat `project_snapshot` and `snapshotTranscriptionId` as internal legacy implementation names, not product concepts and not a lightweight snapshot/reference model.
- `project_transcriptions.id` is the durable project-local transcription identity used by the cloud layout; `project_transcriptions.transcription_id` points to the editable full transcription row owned by the project.
- Collations are semantically project-bound, even though `collations.project_id` is nullable in the schema. New project workflows should require a project, and a later migration can make the database invariant stricter if needed.
- Checkpoint tables already support explicit committed revisions with optional messages. Autosave currently writes working rows directly; cloud serialization rejects dirty working rows whose content hash does not match the current committed checkpoint.
- Cloud file layout is already project-contained: `project.json`, `transcriptions/{projectTranscriptionId}.json`, `collations/{collationId}.json`, `history/...`, and `tombstones/...`.
- Sync primitives exist for committing and publishing project transcriptions/collations, but project-level UI, backup-location management, restore, fork, and opt-in pull orchestration are incomplete.

## Recommended Architecture Decisions

- Make `Project` the central top-level data object. Project list, backup, restore, safe removal, and sync status should all start from projects.
- Keep projects self-contained in every backup target. Each project folder contains full project metadata, full project transcription data, full collation data, version history, and tombstones needed to restore or share that project.
- Do not use shared cloud transcription references or lightweight cloud transcription stand-ins. Reusable library transcriptions may remain local source material, but adding one to a project copies the full transcription into that project.
- Keep a reusable local transcription library only as source material. It is not the live object that project collations depend on and is not uploaded as a separate global dependency for project restore.
- Make cross-project transcription reuse explicit. A project transcription can be refreshed or copied from a committed source version, but no library edit or project edit should silently update another project.
- Treat autosave as local working state only. A checkpoint is the intentional local commit with an optional message. Version history applies to both project transcriptions and collations.
- Treat cloud/local-folder backup as an explicit project operation that uploads committed project-contained files. It must not publish uncommitted autosaved working state.
- Let a local database hold many projects from any source: local-only, Dropbox, Google Drive, local folder, mock/dev, or future providers. The project list should show each project's backup source/target status.
- Support project forking by creating a new local project ID, copying the full project data, and backing the fork up to a selected provider/folder. Forked projects can coexist in the same local database and sync independently.
- Treat collation witness versions as pinned. Updating a project transcription does not silently update existing collation witnesses; a witness refresh is a separate explicit operation.
- Poll configured backup targets periodically to detect newer remote project data. Prompt the user to pull remote updates; do not silently overwrite local project data. Full conflict-resolution UX is out of scope for now because concurrent edits are assumed not to happen.

## Subplan 1: Domain Vocabulary and Status APIs

Goal: Make the project-centered model explicit in code and UI vocabulary before adding more sync UI.

Work:
- Define product terms: Project, Project Transcription, Library Source Transcription, Project Remote Location, Forked Project, Collation Witness Source, Checkpoint, Cloud Backup.
- Add repository/service read models that expose both internal transcription row IDs and stable project transcription IDs. The current project UI mostly sees `transcription_id`; sync/version UI needs `project_transcriptions.id` too.
- Add status helpers for project transcriptions: source/provenance, source checkpoint/hash, current project transcription checkpoint/hash, dirty-to-checkpoint, and available newer source checkpoint.
- Add status helpers for collations: dirty-to-checkpoint, witness source pinned version, witness source available version, and cloud backup state.
- Add status helpers for project remote locations: local-only, provider/folder label, linked backup targets, last backup, pending backup, and available remote updates.

Likely files:
- `app/src/lib/client/db/repositories/projects.ts`
- `app/src/lib/client/db/repositories/transcriptions.ts`
- `app/src/lib/client/db/repositories/collations.ts`
- `app/src/lib/client/db/repositories/revisions.ts`
- `app/src/lib/client/collation/project-collation.ts`
- `app/src/lib/client/db/client.ts`
- `app/src/lib/client/db/rpc.ts`

Expansion notes:
- Prefer adding explicit read models over changing existing minimal list APIs in place.
- No schema change should be required for the first version of this subplan.

## Subplan 2: Local Commit UX for Transcriptions and Collations

Goal: Separate autosave from intentional version creation in the UI.

Work:
- Add a local commit action for project transcriptions using `createCommittedTranscriptionCheckpoint`.
- Add a local commit action for collations using `createCommittedCollationCheckpoint`.
- Show two statuses where relevant: autosave state and committed-version state.
- Allow an optional commit message/label.
- Disable or warn on cloud backup when working state has not been committed.

Likely files:
- `app/src/lib/client/db/repositories/revisions.ts`
- `app/src/lib/components/transcriptionEditor/TranscriptionEditor.svelte`
- `app/src/routes/transcription/[id]/+page.svelte`
- `app/src/lib/client/collation/collation-state.svelte.ts`
- `app/src/lib/components/collation/CollationWorkspace.svelte`
- `app/src/lib/components/collation/AutoSaveIndicator.svelte`
- `app/src/routes/collation/[id]/[phase]/+page.svelte`

Expansion notes:
- The transcription editor currently edits any transcription by row ID. Project-aware commit UI needs to know when the open transcription is project-owned and what its `project_transcriptions.id` is.
- The collation state already has autosave state (`saveStatus`); add checkpoint state without replacing autosave.

## Subplan 3: Project Transcription Refresh and Cross-Project Reuse

Goal: Provide explicit UI for updating project transcriptions from committed source versions and for reusing updates across projects without shared live references.

Work:
- On the Projects page, show each project transcription with its source/provenance and version status.
- Add an action to refresh a project transcription from a selected committed source checkpoint.
- If the source has uncommitted edits, prompt the user to commit the source first.
- Preserve `project_transcriptions.id` when refreshing so collations and cloud paths keep stable identity.
- Add a separate flow to copy/promote a project transcription back into the reusable local library, or to copy a project transcription from another local project, so a transcription corrected inside one project can intentionally become source material for another project.

Likely files:
- `app/src/lib/client/db/repositories/projects.ts`
- `app/src/lib/client/db/repositories/transcriptions.ts`
- `app/src/lib/client/db/repositories/revisions.ts`
- `app/src/lib/client/collation/project-collation.ts`
- `app/src/routes/projects/+page.svelte`
- `app/src/lib/components/projects/ProjectTranscriptionsEditor.svelte`
- Potential new project transcription version/status component under `app/src/lib/components/projects/`

Expansion notes:
- Do not auto-refresh project transcriptions when the library source changes.
- Do not auto-refresh other projects when one project updates a copy.
- This subplan answers the question "do transcriptions exist within projects?" with "yes, project transcriptions are full project-owned data; library transcriptions are reusable local sources only."

## Subplan 4: Collation Witness Version Refresh

Goal: Let users intentionally update a collation to use newer committed transcription content.

Work:
- Show each collation witness with its pinned `source_revision_id` / `source_content_hash` and whether its project transcription has a newer committed checkpoint.
- Add an action to refresh one witness, all stale witnesses, or choose a specific checkpoint.
- Refreshing a witness updates witness source metadata and the collation working state, then marks the collation dirty-to-checkpoint.
- Require a collation commit before cloud backup can upload the refreshed collation.

Likely files:
- `app/src/lib/client/db/repositories/collations.ts`
- `app/src/lib/client/db/repositories/revisions.ts`
- `app/src/lib/client/collation/collation-state.svelte.ts`
- `app/src/lib/components/collation/SetupPhase.svelte`
- `app/src/lib/components/collation/CollationWorkspace.svelte`
- `app/src/lib/components/collation/AutoSaveIndicator.svelte`

Expansion notes:
- Existing save logic already stores witness source revision/hash when saving projections. Add explicit refresh commands rather than relying on incidental resaves.
- Existing collations should remain pinned until the user chooses to refresh.

## Subplan 5: Intentional Cloud Backup and Project Publish UI

Goal: Make cloud backup feel like "commit and push," not invisible autosync.

Work:
- Add project-level backup orchestration that uploads `project.json`, latest committed project transcription primaries/history, latest committed collation primaries/history, and tombstones.
- Treat `project.json` as the project manifest. It should include each project transcription and collation's current committed checkpoint ID/content hash plus tombstone summaries so a remote project can be checked without downloading every primary file. Full version history remains in `history/...` files.
- Add per-entity on-demand upload for collations and project transcriptions.
- Reuse `publishEntity`, `commitProjectTranscriptionForSync`, `commitCollationForSync`, and `syncProjectTombstones` where possible.
- Add a project sync panel showing provider/folder, uncommitted local edits, committed-not-backed-up items, remote update availability, conflicts, and last backup time.
- Add project list summary labels for each project's backup target: local only, provider/folder, multiple backup targets, unavailable provider, pending backup, and remote update available.
- Add a `Fork project` or `Copy project to new backup` flow that creates a new project ID, copies full transcription/collation/history data locally, then backs the fork up to a selected provider/folder.
- Keep background polling separate from explicit backup. Polling should read the remote project manifest, compare remote committed heads with local committed heads and last-seen remote heads, then prompt the user to pull. It must not silently upload or overwrite local work.

Likely files:
- `app/src/lib/client/sync/sync-manager.ts`
- `app/src/lib/client/sync/cloud-files.ts`
- `app/src/lib/client/sync/sync-service.svelte.ts`
- `app/src/lib/client/db/repositories/cloud-connections.ts`
- `app/src/lib/components/SyncStatusIndicator.svelte`
- `app/src/lib/components/CloudConnectButton.svelte`
- `app/src/routes/projects/+page.svelte`
- `app/src/lib/components/collation/CollationWorkspace.svelte`

Expansion notes:
- `serializeProjectCloudFile` exists, but project manifest publishing needs to be wired into a project-level backup operation.
- Upload should be disabled or prompt for commit when an entity is dirty-to-checkpoint.
- Global/library transcriptions should not be uploaded outside a project folder in this subplan.

## Subplan 6: Cloud Project Browser and Local Sync/Restore

Goal: Let users browse valid cloud project folders, import them into the local OPFS database, and opt into pulling remote updates for linked projects.

Work:
- Add a project browser that lists provider folders containing valid `project.json` files.
- Show each cloud project as not local, already linked, conflicting with a local project, or unavailable/quarantined.
- Add actions to sync locally, link to an existing local project, open an already linked project, or pull available remote updates after user confirmation.
- Implement project import in dependency order: project metadata, project transcription primaries, transcription history, collation primaries, collation history, tombstones, then sync metadata.
- Preserve remote IDs and cloud file IDs/revisions where available to avoid duplicate uploads after restore.
- Add periodic polling of linked project folders to detect newer remote project manifests/entity heads and surface an opt-in pull prompt. Assume no concurrent local/remote edits for now; if both changed, show a conservative warning rather than building full conflict resolution.

## Subplan 7: Local Filesystem Provider

Goal: Treat a user-selected local folder as another backup provider using the same project folder layout and UI.

Work:
- Refactor provider/auth concepts so providers are not required to be OAuth-based.
- Add a File System Access API provider implementing the same file operations as Dropbox/Google Drive.
- Persist or recover directory access appropriately. If `FileSystemDirectoryHandle` persistence is needed, store the structured-clone handle in IndexedDB keyed by connection ID and keep SQLite metadata as the provider connection record.
- Add "Local folder" to the provider picker/connect UI.
- Ensure the cloud project browser, project backup panel, remote-update polling, and restore flow work against the local folder provider.

Likely files:
- `app/src/lib/client/sync/providers/provider.ts`
- New provider under `app/src/lib/client/sync/providers/`
- `app/src/lib/client/sync/cloud-auth.ts` or a new provider-connection service
- `app/src/lib/client/db/repositories/cloud-connections.ts`
- `app/src/lib/components/CloudConnectButton.svelte`
- `app/src/lib/client/transcription/external-sync-service.ts` for comparison only, not as the final project backup model

Expansion notes:
- This should not create a second project file format. It should write the same `Apatosaurus/Projects/{projectId}` layout.
- Browser support must be feature-detected. Mobile users can continue using OAuth providers.

## Subplan 8: Backup Health, Safe Local Removal, and Space Management

Goal: Make it clear when local project data can be removed and later restored from a selected backup target.

Work:
- Derive backup health from dirty state, committed checkpoints, tombstones, remote metadata, conflict state, and provider reachability.
- Show project-level statuses: local only, uncommitted changes, committed pending backup, backed up, conflict, and unknown provider state.
- Add a safe-to-remove checklist for each project.
- Add a remove-local flow that warns unless the selected provider/folder has a complete current backup.
- Support "Back up everything first" from the remove-local flow.

Likely files:
- `app/src/lib/client/sync/sync-manager.ts`
- `app/src/lib/client/sync/sync-service.svelte.ts`
- `app/src/lib/client/db/repositories/revisions.ts`
- `app/src/lib/client/db/repositories/cloud-connections.ts`
- `app/src/routes/projects/+page.svelte`
- `app/src/lib/components/SyncStatusIndicator.svelte`

Expansion notes:
- Prefer deriving status rather than persisting another status table unless performance becomes a problem.
- "Safe" should mean restorable from the selected provider/folder now, not merely backed up sometime in the past.

## Suggested Sequence

1. Subplan 1: establish terms/status read models.
2. Subplan 2: add local commit UX.
3. Subplan 3: add project transcription refresh/reuse UX.
4. Subplan 4: add collation witness refresh UX.
5. Subplan 5: add intentional cloud backup/publish UX plus project fork/copy-to-new-target.
6. Subplan 6: add cloud project browse, restore, remote polling, and opt-in pull.
7. Subplan 7: add local filesystem provider.
8. Subplan 8: add safe local removal and space-management flows.

This order keeps the core invariant stable: local autosave creates working state, explicit checkpoints create versions, and backups only publish committed project-contained artifacts.

## Verification Strategy

For each implementation subplan:
- Run `bun run check` from `app/`.
- Run `bun run db:check` from `app/` after schema/type-affecting changes.
- Run targeted unit tests for changed areas, especially `src/lib/client/sync/cloud-files.spec.ts`, `src/lib/client/sync/sync-manager.spec.ts`, `src/lib/client/db/repositories/*.spec.ts`, and relevant collation/transcription specs.
- For Svelte component edits, run the Svelte autofixer/MCP validation on edited `.svelte` or `.svelte.ts` files before finalizing.

End-to-end manual flows to cover as subplans land:
- Create a library transcription, add it to a project, confirm a full project transcription is created.
- Edit the project transcription, confirm autosave updates local working state but cloud backup is blocked until commit.
- Commit the project transcription, back it up, and confirm primary/history files are written.
- Edit the library transcription, confirm the project transcription does not silently change, then explicitly refresh the project transcription.
- Create a collation from project witnesses, refresh a stale witness version, commit the collation, and upload it on demand.
- Browse mock/cloud project folders, import a project into an empty local database, and open its transcriptions/collations.
- Poll a linked project folder with newer remote data, confirm the user is prompted to pull, then pull the update explicitly.
- Fork a project to a new project ID and back it up to another provider/folder.
- Connect a local folder provider, back up a project, reset/remove local state, and restore from that folder.
- Attempt local project removal with uncommitted or unbacked-up work and confirm the UI blocks or warns clearly.
