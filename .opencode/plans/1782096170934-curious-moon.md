# Project-Only Transcriptions And Cloud Storage Plan

## Scope

Implement project-only transcription creation/import, automatic default project support, storage writes on creation and commit, tombstone-based project deletion, and stable slugged project cloud folders.

This is a greenfield change. Do not add migration/backfill compatibility for existing browser data. It is acceptable for existing local browser databases to be reset during development/testing.

## Product Decisions

- Transcriptions are always project-owned. There is no user-visible standalone/global/library transcription list.
- Every user gets an auto-created `Default` project.
- Creating/importing a transcription must put it in a project. If the user does not choose one, use the `Default` project.
- Creation/import writes an initial committed version so existing cloud serializers can publish immediately.
- Committing a transcription/collation should write through to any configured project storage target, not just leave backup pending.
- Cloud project deletion uses tombstones and manifest updates. Do not recursively delete provider folders.
- Project cloud folders use an immutable slug based on the initial project name plus a unique suffix. Renaming a project does not rename the cloud folder.

## Current Relevant State

- `transcriptions.scope_type` defaults to `global`, and `project_id` is nullable in `app/src/lib/client/db/migrations/0001_initial.sql`.
- `buildTranscriptionRow()` in `app/src/lib/client/db/repositories/transcriptions.ts` creates `scope_type: 'global'` and `project_id: null`.
- `/transcription/(library)/+page.svelte` lists standalone/global transcriptions via `listTranscriptionSummaries()`.
- `TranscriptionForm.svelte`, `create-transcription.ts`, and IGNTP import do not pass a project ID.
- Project sync already has provider write primitives: `backupProject()`, `backupProjectEntity()`, `publishEntity()`, and `publishProjectManifest()` in `app/src/lib/client/sync/sync-manager.ts`.
- Cloud serialization requires committed project snapshots. `serializeProjectTranscriptionCloudFile()` rejects non-`project_snapshot` rows and dirty rows.
- Cloud project paths are currently ID-based through `projectCloudRootPath(projectId) => Apatosaurus/Projects/${projectId}` and `ProjectBackupPanel.defaultProjectFolderPath(id)`.
- Existing tombstones cover project-transcription/collation entities. There is no project-level deletion tombstone.

## Phase 1: Local Schema And Project Slugs

Update `app/src/lib/client/db/migrations/0001_initial.sql` directly because this is greenfield.

- Add a persisted slug column to `projects`, for example `storage_slug TEXT NOT NULL UNIQUE`.
- Consider adding `is_default INTEGER NOT NULL DEFAULT 0` only if implementation needs to identify the default project after other projects exist. Otherwise keep the default-project rule in repository logic to minimize schema.
- Make project-owned transcriptions the only shape for transcriptions:
  - Change `transcriptions.scope_type` default from `global` to `project_snapshot` or remove reliance on a default.
  - Make `transcriptions.project_id TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE`.
  - Keep `project_transcriptions` as the explicit project membership row because sync/checkpoint code uses project-transcription IDs.
- Make `collations.project_id` `NOT NULL REFERENCES projects(id) ON DELETE CASCADE` if all collations are also expected to stay project-owned. The repository already treats `projectId` as required in creation paths.
- Add a project-level tombstone shape. Minimal option: allow `sync_tombstones.project_id` to be nullable and use `entity_type = 'project'`, `entity_id = projectId`, `cloud_path = project slug root`, with the tombstone file written outside the deleted project folder. Better option: add a separate `project_tombstones` table so deleting the local `projects` row does not cascade away the tombstone.
- Regenerate `app/src/lib/client/db/types.generated.ts` with `bun run db:generate` from `app/`.
- Keep `schema-version.generated.ts` at version 1 unless the implementation chooses to add a new migration file. Since this is greenfield, prefer editing `0001_initial.sql` only.

## Phase 2: Project Repository Defaults And Slugs

Update `app/src/lib/client/db/repositories/projects.ts` and call sites.

- Add a slug helper near project creation:
  - Normalize initial project name to lowercase ASCII.
  - Replace runs of non-alphanumeric characters with `-`.
  - Trim leading/trailing `-`.
  - Fall back to `project` when empty.
  - Append a short unique suffix, for example `${base}-${nanoid(8)}`.
- Extend `CreateProjectInput` with optional `storageSlug` for restore/import tests and cloud project import.
- Make `createProject()` set `storage_slug` from `input.storageSlug ?? generateProjectStorageSlug(input.name)`.
- Make `ProjectOption` and `ProjectRecord` expose `storageSlug`.
- Make `forkProject()` create a fresh slug from the fork’s initial name instead of copying the source slug.
- Make `updateProjectMetadata()` leave `storage_slug` untouched on rename.
- Add `ensureDefaultProject(db): Promise<ProjectRecord | ProjectOption>` or `ensureDefaultProjectId(db): Promise<string>`:
  - If a `Default` project or `is_default` project already exists, return it.
  - If there are no projects, create `Default` with default collation settings and return it.
  - If there are projects but no default, either create `Default` or choose the earliest project as default. Prefer creating `Default` only when no projects exist unless the implementation adds `is_default`.
- Call default-project creation during worker initialization after migrations, or from project/transcription creation RPCs before returning lists. The most consistent place is `db.worker.ts` after `applyLocalDbMigrations(db)` and Kysely init.

## Phase 3: Project-Only Transcription Creation

Update `app/src/lib/client/db/repositories/transcriptions.ts`.

- Change `CreateTranscriptionInput` to require `projectId: string`.
- Return both IDs from create APIs so UI can navigate by owned transcription ID while sync can publish by project-transcription ID. Suggested result:
  - `transcriptionId`
  - `projectTranscriptionId`
  - `projectId`
- In `createTranscription()` and `createTranscriptions()`:
  - Validate the target project exists, or call `ensureDefaultProjectId()` when projectId is omitted at a higher API layer.
  - Insert `transcriptions` rows as `scope_type: 'project_snapshot'`, `project_id: projectId`, and `origin_type: 'project_snapshot'` or a clearer local-origin value.
  - Insert matching `project_transcriptions` rows in the same transaction.
  - Replace verse index rows as today.
  - Touch `projects.updated_at`.
- Create an initial committed checkpoint before returning. Reuse `createCommittedTranscriptionCheckpoint()` after inserting the project-transcription row, or extract shared checkpoint creation logic so the transaction can remain atomic.
- Remove global filters from summary APIs or replace them with project-specific APIs:
  - `listTranscriptionSummaries(db, projectId)` should list project-owned transcriptions for a project.
  - `getTranscriptionSummary()` should not require `scope_type = 'global'`.
  - If the standalone library route is removed, delete summary APIs that only served it.
- Keep lower-level `getTranscription(id)` by owned transcription ID because the editor route already uses that shape.

## Phase 4: RPC And Client API Shape

Update `app/src/lib/client/db/rpc.ts`, `client.ts`, and `db.worker.ts`.

- Adjust `transcriptions.create` and `transcriptions.createMany` response types from `string`/`string[]` to the new creation result object(s).
- Add a project/default API if useful:
  - `projects.ensureDefault`
  - or make `projects.list`/worker init guarantee it.
- Update worker handlers to invalidate `projects`, `transcriptions`, and `cloud-project-folders` as needed after project-aware creation.
- Add a single worker-side helper for provider-backed writes to avoid duplicating connection/provider creation:
  - Load the first or selected `cloud_project_folders` row for the project.
  - Load its `cloud_connections` row.
  - Create the provider with credential refresh callbacks.
  - Call `backupProjectEntity()` for the created/committed entity or `backupProject()` for whole-project create/delete operations.
  - Swallow/report provider errors as sync results, not as failed local saves, unless the user explicitly requested strict cloud writes.

## Phase 6: Sync Writes On Create And Commit

Use existing sync primitives in `app/src/lib/client/sync/sync-manager.ts` where possible.

### On Create/Import

- After project-owned transcription creation and initial checkpoint creation, attempt cloud write if the project has a configured `cloud_project_folders` row.
- Use `backupProjectEntity(context, { entityType: 'project-transcription', entityId: projectTranscriptionId })` so the primary file, history file, and manifest get written.
- For bulk IGNTP import, prefer one `backupProject()` after all creations instead of one provider write per transcription. This reduces provider calls and ensures the manifest includes all imports.
- If no storage target exists, creation still succeeds and remains local.
- If provider write fails, local creation still succeeds and the UI shows sync pending/error state.

### On Commit

- Replace UI calls to `createCommittedTranscriptionCheckpoint()` where storage context exists with a new RPC such as `revisions.commitTranscriptionAndSync` or add sync behavior behind the existing commit RPC.
- For transcription commits:
  - Create committed checkpoint.
  - If linked storage exists, call `backupProjectEntity()` for the project-transcription.
  - Return checkpoint plus optional sync result.
- For collation commits:
  - Create committed checkpoint.
  - If linked storage exists, call `backupProjectEntity()` for the collation.
  - Return checkpoint plus optional sync result.
- Update `app/src/routes/transcription/[id]/+page.svelte` to show `Committed and synced` when sync succeeds, or `Committed locally; sync pending` when provider write fails/unavailable.
- Audit collation commit UI/state for equivalent messaging.

## Phase 7: Project Cloud Paths And Slugged Folders

Update `app/src/lib/client/sync/cloud-paths.ts`, `cloud-files.ts`, `project-restore.ts`, `ProjectBackupPanel.svelte`, and tests.

- Change `projectCloudRootPath()` to accept a project record or storage slug instead of only project ID:
  - `Apatosaurus/Projects/${storageSlug}`.
- Make default folder binding use `project.storageSlug`.
- Include `storage_slug` in `ProjectCloudFile` so restored/imported projects preserve their original cloud folder slug when possible.
- Bump `CLOUD_FILE_SCHEMA_VERSION` because cloud project manifests gain a required field.
- Update `parseProjectCloudFile()` and `projectCloudFileToRepositoryInput()` for `storage_slug`.

- Keep project folder slug immutable on rename. Only `project.json` content should update the display name.

## Phase 8: Tombstone-Based Project Deletion

Implement project deletion as a logical delete that publishes tombstones and manifest changes, not provider-folder deletion.

- Add a repository function such as `deleteProjectWithTombstone(db, input)` distinct from `removeLocalProject()`:
  - Gather project cloud folder path/slug and entity paths.
  - Create a project-level tombstone record before deleting local project rows.
  - Preserve enough tombstone information after local project deletion. A separate `project_tombstones` table is safest because current `sync_tombstones.project_id` cascades with `projects`.
  - Delete local project rows through normal cascades.
- Add sync support for project tombstones:
  - Write tombstone file under a stable global tombstone area such as `Apatosaurus/Tombstones/projects/${projectId}.json`, not under the deleted project folder.
  - Optionally update an account-level project index if one exists or is added. If not, project deletion is represented by tombstone file discovery.
  - Do not call provider recursive delete on `Apatosaurus/Projects/${storageSlug}`.
- Update cloud project listing/import to recognize project tombstones and suppress deleted projects from candidates.
- Keep `removeLocalProject()` as local-only removal of a backed-up copy; it should not create a project deletion tombstone.
- Add UI copy that distinguishes:
  - `Remove local copy`: keeps cloud backup.
  - `Delete project`: tombstones deletion for sync and removes local project.

## Phase 9: Remove Standalone/Global Promotion Paths

Audit and remove or repurpose global/library-specific project APIs.

- `promoteProjectTranscriptionToLibrary` should be deleted or hidden because there is no library.
- `listProjectTranscriptionOptions()` should stop returning global rows; it should return project-local candidates and cross-project committed source candidates where needed.
- `syncProjectTranscriptionIds()` should no longer clone global sources. It should either manage project-owned rows only or use `addProjectTranscriptionFromProject()` for cross-project copies.
- `origin_type === 'canonical'` and `scope_type === 'global'` branches should be removed unless needed for imported cloud files. Greenfield means they are not needed.
- Update UI components that mention library promotion.

## Risks And Notes

- The editor route uses owned transcription IDs, while cloud sync uses project-transcription IDs. Creation results must include both to avoid route churn.
- Initial cloud write requires an initial committed checkpoint. Do not attempt to serialize an uncommitted project transcription.
- Automatic provider writes should not make local save/commit fail unless the user explicitly asked for strict cloud behavior.
- Dropbox configuration errors such as missing `PUBLIC_DROPBOX_CLIENT_ID` should surface as provider/sync errors, not as failed local data creation.
- Local folder provider writes only happen when sync code calls provider APIs. Binding a folder alone is not enough.
- Avoid backward compatibility branches unless an existing test fixture must be deliberately retained.
