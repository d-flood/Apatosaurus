## Current Product Decisions

- `Project` is the top-level aggregate users work with, back up, restore, fork, and remove locally.
- Both transcriptions and collations belong to projects for sync/backup purposes.
- A project backup must contain full project transcription data and full collation data.
- Do not use shared cloud transcription references or lightweight transcription stand-ins.
- The current schema still uses legacy internal names such as `scope_type = 'project_snapshot'`; do not expose "snapshot" as product language.
- Historical versions are committed checkpoints and `history/...` files, not snapshots.
- Autosave writes local working state only.
- A local commit/checkpoint is the intentional version boundary and may include an optional message.
- Backup uploads committed project-contained files only; it must not upload uncommitted autosaved state.
- A local database can contain many projects from local-only, Dropbox, Google Drive, local folder, mock/dev, or future sources.
- The project list should show each project's backup location or `Local only` status.
- Forking creates a new project ID, copies full project data, and can back up to a chosen provider/folder.
- Polling remote storage should detect remote updates and prompt for an opt-in pull.
- Full conflict resolution is not in scope yet; assume no concurrent edits and warn conservatively if local and remote both changed.

## Version and Freshness Model

Use committed checkpoint identity for scholarly/application versions.

- Entity version identity is `{currentRevisionId, currentContentHash}`.
- Provider revisions such as Dropbox `rev` or Google Drive ETag are transport metadata only.
- `project.json` is the remote project manifest and cheap freshness index.
- The manifest should summarize current heads for project transcriptions, collations, and tombstones.
- The manifest does not need to duplicate every historical checkpoint in the first implementation.
- Full history stays in `history/transcriptions/...` and `history/collations/...`.
- A local entity is up to date with remote when its committed checkpoint ID/hash matches the entity head in the last verified remote manifest.
- Upload entity history and primary files before uploading `project.json`, so the manifest never advertises heads whose files are missing.

## Terminology Rules

Use these terms in new UI, APIs, and docs:

- `Project`
- `Project transcription`
- `Project transcription ID` for `project_transcriptions.id`
- `Project-owned transcription row` or `projectOwnedTranscriptionId` for the underlying `transcriptions.id`
- `Library transcription` for reusable local source material
- `Committed version` for user-facing checkpoint language
- `Backup location` or `Remote backup` for provider/folder links
- `Fork project` for creating a new independent project ID

Avoid these terms in new public names:

- `Snapshot`
- `Project copy`
- `Global transcription` in user-facing UI

Allowed legacy references:

- `scope_type = 'project_snapshot'`
- `snapshotTranscriptionId`
- Existing function names such as `addProjectTranscriptionSnapshot` or `loadProjectTranscriptionSnapshot`

When legacy names appear, explicitly label them as internal compatibility details.

## How To Update Progress

At the end of each implementation session:

1. Update the relevant row in the progress table.
2. Add a concise note to `Current Progress` with what landed.
3. Set `Next Action` to the next smallest useful slice.
4. If verification failed or was skipped, record that in the row.
5. If a subplan's acceptance criteria changed, update the subplan file too.

Keep progress notes factual and brief. Do not use this file as a detailed changelog.

## Cross-Cutting Acceptance Criteria

Every completed implementation slice should preserve these invariants:

- Project backup/restore remains project-contained.
- Project transcriptions are full data owned by the project.
- Collations are associated with projects.
- Autosave and committed versions remain separate.
- Backup uploads committed versions only.
- Remote polling prompts before pull.
- No new user-facing snapshot terminology is introduced.
- Provider-specific file revisions are not used as application version identity.
- Tests or manual verification cover the changed behavior.

## Verification Defaults

Run relevant checks from `app/` after implementation changes:

```sh
bun run check
bun run db:check
```

Run targeted unit tests listed in the active subplan. For Svelte changes, run the repo's Svelte validation/autofixer workflow on edited `.svelte` or `.svelte.ts` files.

For planning-only edits, code tests are not required, but review the changed Markdown for terminology drift.
